# v0.28.0 — The lane that was never green, and two values nobody was told to set

Release date: 2026-09-12

Bump level: **MINOR** (`docs/RELEASING.md` §1.2). It adds a file to the
scaffolded output and corrects adopter-facing setup instructions, so §1.1 PATCH
does not apply.

## Why this release exists

v0.27.0 claimed *"L3 golden path E2E — green on `main`"*. That covered
`golden-path.yml`. It did not cover `golden-path-extended.yml`, the lane that
proves the **closed loop** — `/predict`, the prediction log, the `/metrics`
counter — and that lane had **never once been green**.

The three fixes below are what make an L4 attempt possible. An adopter on
v0.27.0 has a runbook that is wrong about where two AWS values go and an image
carrying two fixable HIGH advisories.

## The closed-loop lane: four stacked causes

Every `kubectl apply` in it succeeded and every resource was created. In every
failed run the pods were `Running`, `Ready` and 0-restart. **The service was
never the problem.** Each cause was hidden behind the previous one, so this
took one CI round-trip per fix.

| # | Cause |
| --- | --- |
| 1 | The tolerance filter assumed **one** stderr line per error. kubectl emits two: `ensure CRDs are installed first` carries no kind name and survived a grep keyed on `no matches for kind "…"`. **With this alone the lane could never have been green, from its first run.** |
| 2 | The filter could not tell a `Warning:` from an error — and there was one, from a duplicate `ENVIRONMENT` env var (`env[3] = dev`, `env[9] = ci`). Kubernetes keeps one and only warns, so which value the pod gets was decided by the apply path rather than by the manifest. |
| 3 | `kubectl port-forward … &` was backgrounded **in its own step**. Actions reaps a step's children when it ends, so the tunnel was dead before the first curl: `Failed to connect to localhost port 8000 after 0 ms`. |
| 4 | It forwarded `8000:8000`, and the Service publishes `port: 80` with `targetPort: 8000`. There is no service port 8000 to forward. |

`golden-path.yml`'s smoke job had always done it the working way — one step,
`18000:80`. This lane now mirrors it.

## Two AWS values an adopter could not have known to set

Nobody had completed an L4 deployment, so nobody had found these. Both fail on
the **first** real AWS deploy.

- **`AWS_BUILD_ROLE_ARN` appeared in no runbook.** `deploy-aws.yml`'s build job
  reads it from `secrets` to push to ECR. Two roles rather than one is
  deliberate — ADR-017 / D-31, per-purpose identities — and the second was
  never written down.
- **`AWS_ROLE_ARN` was documented in the wrong channel.** Read from `secrets`;
  §A.4 said *"Add repository variables (NOT secrets — these are not
  sensitive)"*. The reasoning is sound and the code disagreed. **GitHub does
  not fall back**, so the value arrives empty and the failure names the
  consumer. This half is the more dangerous one: a missing secret looks unset,
  while a value in the wrong channel looks configured.

The GCP side was consistent throughout, which makes the AWS mismatch drift
rather than design. `scripts/check_deploy_contract_documented.py` (gate 19) now
asserts every `vars.*`/`secrets.*` a deploy workflow reads is documented **in
the channel it is read from**.

> The channel check is the *second* attempt. A proximity heuristic produced
> **eleven false positives** against a tree with one real mismatch. A control
> that is wrong eleven times out of twelve sends its reader to edit
> documentation that was already right. It is table-scoped and exact now, and
> one of the six regression tests pins that precision rather than the detection.

## The image gate caught a new CVE three days after going green

```text
Total: 2 (HIGH: 2, CRITICAL: 0)
libpcre2-8-0  CVE-2026-86145  HIGH  fixed  10.42-1 → 10.42-1+deb12u1
libpcre2-8-0  CVE-2026-89161  HIGH  fixed
```

Neither the Dockerfile nor `requirements.txt` names that package — it arrives
with the base image, and the base image lags Debian's security archive. **That
is the gate working rather than breaking.** Before it existed the image would
have shipped them silently.

The runtime stage applies the distro's pending patches now, verified in the
build log: `Unpacking libpcre2-8-0:amd64 (10.42-1+deb12u1) over (10.42-1)`.
Not baselined — both are fixable by a package upgrade today, and an
expiry-dated suppression for something a one-line change fixes is how a
baseline stops meaning anything.

Trade-off stated: `apt-get upgrade` makes the OS layer non-reproducible across
builds. **It already was** — `apt-get install` without pinned versions resolves
against a moving archive — so this changes the security posture without
changing that property.

## Known follow-ons

Unchanged from v0.27.0 except where noted:

- **24 of 51 declared config fields are read by nothing** — counted and
  ratcheted by `check_config_is_read.py`, each banner-warned in `config.yaml`.
- **The numpy 1.x boundary's rationale is unmeasured** — a 2024-era claim now
  defended by a gate.
- **Dependabot still opens per-directory PRs for some shared pins.**
- **The AWS/GCP channel asymmetry is recorded, not resolved.** AWS reads role
  ARNs from `secrets` while GCP reads its equivalents from `vars`. Closing it
  would change `deploy-common.yml`'s `workflow_call` contract, which is
  adopter-visible and needs its own ADR.
- **L4 remains unproven.** No cloud deployment is claimed. What changed is that
  the template-side blockers to attempting one are gone.
