# v0.30.0 — Skills where the tools look, and scheduled jobs that can reach the network

Release date: 2026-09-26

Bump level: **`v0.x.0`, MAJOR-class** (`docs/RELEASING.md` §2.1). The skill
pointers in scaffolded output move from `.cursor/skills/<id>.md` and
`.codex/skills/<id>.md` to `.agents/skills/<id>/SKILL.md`, which is a change in
scaffolded paths, so this release carries the full MAJOR paperwork: a
`### Breaking for adopters` block in `CHANGELOG.md` and a matching `from → to`
section in `MIGRATION.md`. No manual action is required with the shipped files.
`v1.0.0` stays reserved for real cloud E2E evidence.

## Why this release exists

**Cursor and Codex discovered none of the skills, in this repository or in any
service scaffolded from it.** All three tools that discover skills load one
only from `<root>/<id>/SKILL.md` with `name` and `description` front-matter, and
each reads specific roots. Only the Claude surface used that layout, after
audit R6. Cursor got flat files, and Codex got flat files in a directory it
never reads. `validate_agentic_manifest.py --strict` stayed green, because it
compared the rendered files with the manifest, and the manifest named those
places (#238, ADR-027 §9).

The same day, the fix's own claim turned out to be wrong. Sharing
`.agents/skills/` does not list each skill once in Cursor, because Cursor also
reads `.claude/skills/` for compatibility. The duplicate cannot be avoided
while Claude reads only `.claude/` and Codex only `.agents/`, so the validator
now requires the copies one tool reaches to be the same skill (#239, ADR-027
§10). Both findings came from ml-platform's QA-4 audits, which found the same
defect downstream first.

**Three scheduled workloads had no network path at all** (#182, #230). The
drift, performance and ground-truth CronJobs carry labels no NetworkPolicy
selected, so under default-deny they could not resolve DNS or reach storage.
`k8s/base/networkpolicy-jobs.yaml` and a patch in every cloud overlay give them
the predictor's allowlist. The control now asks the question for every
workload.

**GitHub Actions had no identity Terraform created** (#183, #231). On GCP the
Workload Identity pool and provider now exist in Terraform, with the
repository pinned; on AWS `drift_ci` and `retrain_ci` are GitHub-trusted roles.
Both are opt-in through `github_repo`.

## Adopter impact

See `MIGRATION.md` § v0.29.0 → v0.30.0. With the shipped overlays and default
variables, `copier update` needs no manual step: the renderer migrates the
skill pointers itself and leaves hand-written files alone.

## Known follow-ons

- **L4 remains unproven.** No cloud deployment is claimed.
- **The numpy 1.x boundary is still unmeasured**, and it blocks the `shap` and
  `pandas` majors.
- **Cursor lists every skill twice.** This cannot be avoided while three tools
  read three different roots. The copies are kept identical.
