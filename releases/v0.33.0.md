# v0.33.0 — MLflow 3.17.2, with the tracking server it talks to

Release date: 2026-10-24

Bump level: **MINOR**. The generated `requirements-train.txt`, `requirements.txt`, `pyproject.toml` and the MLflow
compose file change their pins and the server image, which is changed scaffold output: not a PATCH
(`docs/RELEASING.md` §1.1), and no §1.3 contract changes. `MIGRATION.md` has no entry, because `copier update`
brings the new pins and image and nothing else needs a manual action.

## Why this release exists

**CVE-2026-53995** (HIGH): arbitrary file write through MLflow's FileStore path traversal, fixed in 3.17.2. It was
found by ml-platform, which consumes this template: the generated service's training set failed its Trivy gate
(DuqueOM/ml-platform#134).

- **The client pin admitted the vulnerable release.** `mlflow ~= 3.17.1` allows 3.17.1. It is `~= 3.17.2` now
  in `requirements-train.txt` and `pyproject.toml`, a floor below which nothing resolves.
- **The fix lives in the server, and both servers had been left behind.** `docker-compose.yml` and
  `templates/service/infra/docker-compose.mlflow.yml` ran `ghcr.io/mlflow/mlflow:v3.16.0`. #292 had raised the
  client to 3.17.1 while both servers stayed put, because Dependabot updates the client through pip and the
  server through docker, and it cannot group the two. Raising the client alone would have left every adopter's
  tracking server exposed. Both run `v3.17.2` now, and `test_mlflow_client_server_pin.py` holds the client pins
  and every server image to one version, at least the fixed release.

**The dependency scan resolved on the runner's Python** (#308). The Self-audit job resolved every requirements file
on the runner's system `python3`. When `ubuntu-latest` became ubuntu-26.04, environment markers in pandas 3 and
scikit-learn 1.9 made `examples/minimal` unresolvable beside `numpy ~= 1.26.4`, and the scan failed on every run.
Had it resolved, it would have scanned a set no generated image installs. It now resolves on the Python
`templates/service/Dockerfile` names, as `eda-heavy-smoke.yml` already did.

Also in this release, merged since v0.32.0: pyarrow held below 26 beside numpy 1.x (#301); the test environment
installed at the pins the service declares (#290); one Dependabot PR per action across both trees (#291); and
updates to fastapi 0.150, pydantic 2.14, pandera 0.34, ruff 0.17, mypy 2.4, pre-commit 4.7, boto3,
google-cloud-secret-manager 2.31, great-tables 1.1 and chardet 7.7.

## Adopter impact

- The next `copier update` moves MLflow to 3.17.2 in two files and the tracking server image to `v3.17.2` in the
  compose file. Upgrade the server and the client together: the test now refuses them apart, and a server left on
  3.16 keeps the CVE.
- If your security baseline accepted CVE-2026-53995 for MLflow 3.16 or 3.17.1, the entry can be removed after the
  update.

## Known follow-ons

- **L4 remains unproven.** No cloud deployment is claimed.
- **The numpy 1.x boundary is still unmeasured**, and it now holds pyarrow below 26 as well as the `shap` and
  `pandas` majors.
- **The compose files pin images by tag, not by digest.** A digest is what makes a pulled image the reviewed one;
  moving the compose files to `tag@sha256:` is a change of convention across every image they run, not only
  MLflow's, and is not made here.
- **`examples/minimal` is resolved on the service image's Python (3.13), while its own image runs 3.11.** The
  scan reads the versions the service line would install.
